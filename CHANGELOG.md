## v1.6.0-pre

- Added Z.ai's GLM family via OpenRouter: GLM 5.3 (`open_router_glm_5_3`), GLM 5.3 Flash (`open_router_glm_5_3_flash`), and GLM 5.2 (`open_router_glm_5_2`). All three support temperature, structured outputs, native tool calling, and streaming; 5.3 Flash additionally supports image input while 5.3 and 5.2 are text-only. All three are priced at OpenRouter's current promotional rates (10%, 50%, and 70% off respectively), each recorded with a pricing note.
- `Raif.llm`, `Raif.llm_config`, `Raif.embedding_model`, and `Raif.embedding_model_config` now accept the model key as a String or a Symbol. The registries are symbol keyed and previously looked the key up uncoerced, so a String key raised "No LLM found" while printing the key in the available list; every internal call site symbolized before calling, but a host app passing a String (from an initializer, ENV, or a database column) hit the mismatch. `Raif.register_llm` and `Raif.register_embedding_model` symbolize the key at registration to match, so a model registered under a String key (previously reachable only by String lookup) is now retrievable either way.
- The model manifest is now the runtime registry. `Raif.default_llms`, `Raif.default_embedding_models`, and `Raif.default_streaming_unsupported_model_keys` are built at boot from `lib/raif/model_manifest/definitions/*.rb` (moved from `model_manifest/` so the gem ships them), and the generated `lib/raif/default_llms.rb`, `lib/raif/default_embedding_models.rb`, `en.yml` model name sections, install initializer key list, and setup docs key lists, along with `bin/generate_llm_registry` and the freshness spec that policed them, are gone. Registered keys, api names, costs, settings, and deprecation flags are unchanged. Every `Raif::Llm` now exposes read-only `lifecycle`, `pricing`, and `capabilities` hashes (plus `lifecycle_status`, `added_on`, `deprecated_on`) and every `Raif::EmbeddingModel` exposes `lifecycle` and `pricing`, so host apps can read what Raif knows about a model. Model names come from each definition's `display_name`; a host app's own `raif.model_names.<key>` locale entry still takes precedence.
- Fixed streamed Gemini responses losing their function calls, which surfaced as `Raif::Errors::BlankResponseError` ("returned no text response and no tool calls") whenever a Gemini 3 model (e.g. `google_gemini_3_5_flash`) answered a streamed request with a tool call. Gemini 3 sends the `functionCall` part in one chunk and then a finish chunk whose only part is an empty text delta; `Raif::StreamingResponses::Google` accumulated parts by their index within each chunk, so the empty text at index 0 overwrote the function call at index 0. Parts are now accumulated in arrival order: text deltas extend the last part while it is text, and any other part is appended. The same fix stops a function call that follows streamed text from replacing that text. Non-streamed requests were unaffected.
- Fixed `Raif::ModelCompletion#provider_managed_tool_calls` never reporting Google code execution. Gemini persists provider-managed code execution as an untyped `executableCode` part followed by a `codeExecutionResult` part, and the extractor only recognized Anthropic `server_tool_use` and OpenAI typed blocks, so the admin model completion page and `tool_call_summary` showed no call even though the model ran the code. Each `executableCode` part (when `Raif::ModelTools::ProviderManaged::CodeExecution` was available) now yields a `code_execution` tool call whose `arguments` hold the language and code, `raw_result` holds the execution result, and `status` carries Gemini's `outcome` (e.g. `OUTCOME_OK`); results are paired by the shared `id` Gemini 3 stamps on both parts, falling back to positional pairing for older models that omit it. A Google response that used both code execution and Google Search reports both: the search call is still inferred from citations whenever no explicit web search call is present, rather than only when no tool call was extracted at all.

- **Behavior Change**: Two providers that stored the prompts they were sent by default no longer do. `Raif::Llms::OpenAiResponses` now sends `store` on every request, defaulting to `false` via the new `Raif.config.open_ai_store_responses` - the Responses API defaults it to `true`, so until now OpenAI kept the response object for 30 days and the prompt was readable in the organization's dashboard and retrievable by response id. `Raif::Llms::OpenRouter` now sends `provider: { data_collection: ... }` on every request, defaulting to `"deny"` via the new `Raif.config.open_router_data_collection`; OpenRouter routes each request to an upstream inference provider, some of which store prompts non-transiently and train on them, and OpenRouter defaults the parameter to `"allow"`, which filters nothing, so the only thing narrowing the routing was an account-level setting on openrouter.ai that a host app cannot read from its own code. A third setting, `Raif.config.open_router_zdr`, sends `provider: { zdr: true }` and is the only one of the three that addresses retention - `data_collection` covers training and non-transient storage, and OpenRouter states it has no routing rules based on providers' retention policies, so a provider that holds prompts for a fixed window without training on them still satisfies `"deny"`. It defaults to `false` and the parameter is omitted unless set, because ZDR is a far narrower filter and many models have no ZDR endpoint at all; OpenRouter treats `false` and absent alike, and OR's a per-request value with the account-wide and guardrail settings, so it can only add enforcement. The other two default to the restrictive value, because an engine cannot know whether its host is allowed to leave prompts with a processor, and because the permissive value is the one a host should have to choose. All three are validated at boot rather than silently coerced. Consequences worth checking before upgrading: `data_collection: "deny"` narrows the endpoints OpenRouter will route to, so a model whose only endpoints collect data now returns a no-endpoints error instead of a completion; and `store: false` also disables provider-side response retrieval, which nothing in Raif relies on today (no code path uses `previous_response_id`) but a host app reaching for a response id would notice. Neither setting amounts to zero retention on its own: OpenAI generates abuse monitoring logs for all API usage and holds them for up to 30 days whatever `store` says, and under an organization approved for Zero Data Retention it treats `store` as `false` regardless, so setting it to `true` there has no effect. `Raif::Llms::OpenAiCompletions` is untouched - `store` already defaults to `false` on Chat Completions. The Batch API path was checked against the live provider, since it validates each entry asynchronously and would report a rejected parameter as a per-entry error in the batch's error file rather than as a response to any call Raif makes: a batch body carrying `store: false` is accepted, every entry completes, and retrieving the resulting response by id returns 404.

- Any of the three settings can be overridden without changing the global posture. A `Raif::Task`, `Raif::Conversation` or `Raif::Agent` subclass sets `self.open_ai_store_responses` / `self.open_router_data_collection` / `self.open_router_zdr` (nil, the default, defers to `Raif.config`), and `Raif::Llm#chat` takes the same three keyword arguments for a one-off. An override is persisted, in a new `request_settings` jsonb column on `raif_model_completions`, because batch submission reloads its completions from the database in a later process and builds the provider request from what it finds: a transient override would be lost there, and the loss is not symmetric - on an app with a permissive global setting, a task that explicitly said not to retain its prompts would have them retained. A bag rather than a column per setting, since each provider has its own knobs and typed columns would add one sparse, mostly-NULL column per provider per knob; `Raif::ModelCompletion::REQUEST_SETTING_KEYS` is the allowed key set and both the keys and their values are validated, so it cannot become a dumping ground. An absent key is the only thing that means "defer to `Raif.config`". The prompt caching and parallel tool call flags stay request-scoped, for one reason and one non-reason. `anthropic_prompt_caching_enabled` is read unconditionally when the request is built, so a batched request from a caching-enabled task omits `cache_control` today and persisting the flag would start sending it - which moves the bill in a direction that depends on prefix reuse against a 5-minute cache TTL, since a batch can take hours and an expired entry pays the 1.25x write premium with no 0.1x read to recover it. That is a cost change, and it belongs on its own rather than inside a privacy fix. The other two simply have no batched request to change: Bedrock has no batch API, and every `allow_parallel_tool_calls` read sits behind a `tool_choice` that `Raif::Task#prepare_for_batch!` never sets. All three values are also listed on the admin config page.

- `raif_tasks` can now be archived and culled, on the same terms `raif_model_completions` already were. A task holds a prompt, a system prompt and a raw response, so the table grows as fast as the completions table and carries the same sensitive text, but nothing could remove a row from it. `Raif::ArchiveTasksJob` archives tasks older than the new `Raif.config.task_retention_period` (nil by default, minimum 1 month, independent of `model_completion_retention_period`) and deletes them, and the batching, partitioning, upload and cull machinery it runs on is the machinery the completion job already used - both are now subclasses of a new `Raif::ArchiveJob`, which owns the invariants, while each subclass contributes only its eligibility rules. `Raif::ArchiveModelCompletionsJob`'s behavior is unchanged. Three things are specific to tasks. A task is never culled while a `Raif::ModelCompletion` row still names it as its source: `Raif::Task` declares `has_one :raif_model_completion, dependent: :destroy`, which a bulk delete does not run, so culling underneath a live completion would leave it pointing at nothing - the completion job archives the completion first and the task follows on a later run. A task referenced by a `raif_prompt_studio_batch_run_items` row is retained indefinitely, because all three of that table's task foreign keys `RESTRICT` and deleting a referenced task would raise and take the cull down with it. And a task's `raif_model_tool_invocations` are archived with it, in their own object under the same partition prefix and deleted in the same transaction - they cannot ride inside the task's object, since each object holds one table and its manifest declares that table's columns, and they cannot be swept up afterwards either, because `raif_model_tool_invocations` has no partition column of its own and the only thing that can place an invocation in a partition is the task it belongs to. There is no durability guard, unlike the completion job's: a task carries no spend of its own, and the cost event that carries it is already made durable by the completion gate.

- Culled tasks are now identifiable in the raif admin. A new `raif_task_archive_id` column on `raif_inference_cost_events` is stamped at cull time, immediately before the task row is deleted, and the admin's task page renders an archived-task view from the surviving cost event - its archive link, model and cost data - instead of raising `RecordNotFound`. It is the task-side twin of `raif_archive_id`, which stamps the archive holding the event's completion, and one column could not have served both: an event routinely has its completion culled while its task is still retained, so both stamps can be set on one event and each names a different object. The stamp is the only proof, as with the completion badge - an event whose task is gone but that carries no stamp belongs to a task deleted outside the archive job, and the admin treats that as missing rather than claiming it was archived. A nonterminal task never produced a cost event, so nothing survives it and its id still 404s. `Raif::Archive.purge_partition!` nullifies both stamps.

- A single eval run can now be read as HTML. `raif evals:report RESULTS.json` renders one results file as a self-contained page and writes it beside the file, or to `--output PATH`. `evals:compare --format html` already existed, but it answers "what moved between two runs" and needs a baseline to do it - so the first run of a suite, and every run made where no comparable baseline exists, had only console output that scrolls away and a results JSON that is not readable by eye. The page leads with the run's header (model, judge, when, shape, cost, the host app's commit, and the capture mode), then the totals, then every expectation that did not pass with the `result_metadata` it recorded, then per-eval pass rates naming the weakest cases, then the score summaries. Below that is every eval in the run as a collapsed `<details>` block carrying its expectations, its scores against their gates, its usage, and its captured model completions. Four things are worth knowing. A gated score writes both a failed expectation and a score whose `passed` is false, so the failures section counts it once, through the expectation, rather than reporting one failure as two. Everything interpolated is HTML-escaped, because expectation metadata and judge reasoning are model output and a report is a file people forward. Under `full` capture - the default - the results file holds prompts and responses, so they are rendered and the footer says which capture mode produced the page, since forwarding a file of prompts is not the same as forwarding one of token counts. And a run that stopped early writes no results file at all, leaving only its `.partial.jsonl` log, which is the obvious thing to reach for and fails to parse for a reason that says nothing about what to do next: it is caught by extension before the parse and pointed at `--resume`. Rails is not booted, for the reason `evals:compare` does not boot it.

- An eval run's `configuration` block now records what it measured, not only how it was configured. A new `datasets` array carries one entry per dataset - the eval set that declared it, its name, its case count, and a SHA-256 `digest` over its cases - and a new `code` object carries the host app's git HEAD and whether the tree was dirty. `evals:compare` joins the two runs on `case_id`, so before this, editing one line of a dataset and re-running reported the difference as the model behaving differently on the same input, with nothing in the output hinting that the input had changed. The digest is taken over cases sorted by id with their keys sorted too, so reordering or reformatting a dataset leaves it alone while editing an input, an `expected`, or the set of cases changes it. `evals:compare` warns loudly and continues when the fingerprints differ - comparing a widened dataset against its predecessor is legitimate, as long as the reader knows that is what they are looking at - and prints each run's commit in its header. `--resume` is stricter about the dataset and looser about the code: a dataset whose digest moved is refused, since the two halves of the results file would describe different inputs under one case id, while a commit landing mid-interruption only warns, because it is often the commit that fixed whatever interrupted the run. Only the datasets both the log and the resuming invocation resolved are compared, so a resume narrowed to one eval set file still works.

- **Behavior Change**: LLM judge spend is now reported apart from the model under test's. Judge calls run inside the eval, so they were counted in a result's `usage` and in the run's `total_cost` with no way to separate them - and `evals:compare` then presented that total as `total cost $1.10 -> $1.64` in a report whose purpose is comparing two models. The judge is held fixed across a comparison by design, so its spend is not part of that difference; it does not cancel out either, because a wordier model gives the judge more to read. Captured completions are now tagged with whether they came from a `Raif::Evals::LlmJudge`, a result whose eval called one gains a `judge_usage` object of the same shape as `usage`, and the run's `summary` gains `total_judge_model_completions`, `total_judge_tokens`, and `total_judge_cost`. These are a subset of the existing figures rather than spend beside them, so no total changed. Both the run summary and `evals:compare` print the model under test and the judge on their own lines beneath the total. A results file written before this shows `-` rather than `$0.00` for judge spend, since unknown is not zero.

- **Behavior Change**: a score summary's `ci95` now needs at least 5 values and says why when it does not have them. It was suppressed only below 2, so the documented three-case dataset produced a percentile bootstrap over 3 case means labelled a 95% confidence interval. Three values have 10 distinct resamples between them, so the interval restates them rather than inferring from them, and its real coverage is neither 95% nor stable - which invites exactly the over-reading the interval was added to prevent. Below the floor the key is replaced with `ci95_omitted`, naming what the sample was short of (`"3 cases; a 95% interval needs 5"`), counted in the unit the spread was measured in, and the console prints the same fragment beside the mean. `Raif::Evals::Statistics::MIN_BOOTSTRAP_SAMPLE` holds the floor.

- Eval sets gain four ground-truth matchers, so a dataset's `expected` has something in the framework that reads it. `expect_exact_match`, `expect_includes`, `expect_matches`, and `expect_within` each wrap `expect`, so they count toward the pass rate and compare across runs like any other expectation. Two things they add over the hand-written `task.parsed_response.downcase.include?(...)` block every dataset eval was writing. Normalization is applied the same way in every eval set - strings are stripped and downcased unless told otherwise - so numbers from two eval sets mean the same thing. And each records what it compared as result metadata (`actual`, `expected`, plus `missing` for a multi-keyword `expect_includes` and `difference` for `expect_within`), where a hand-written block records only that it failed; values over 500 characters are truncated so a long response does not become most of the results file. `expect_within` mirrors RSpec's `be_within(delta).of(expected)` and also takes `percent:` for a relative tolerance. The default descriptions name the check rather than the value (`exact match`, `includes expected text`, `matches expected pattern`, `within 0.5 of expected`) because `evals:compare` tallies an expectation across an eval's cases by its description, and a description carrying case data would split into one tally per case and leave the regression gate reading a rate measured on a single case; pass `label:` to name a check, keeping per-case values out of it.

- **Behavior Change**: an eval that raised is no longer counted as an eval that failed. `ExpectationResult` has carried a distinct `:error` status since evals shipped, and the results JSON preserved it, but every aggregate collapsed it into "not passed" - so a 429, a socket timeout, a provider 500, or a raise in `setup` landed in the same bucket as "the model wrote a worse summary". An error is the absence of a measurement, not a bad one. The run summary gains `errored_evals` and `errored_expectations` and stops folding them into its failed counts (what read `1 failed` now reads `0 failed` / `1 errored`), and a result that raised is written with `errored: true`. Within the eval tooling added in this release, errors are kept out of the quality numbers the same way: errored runs are excluded from `pass_rate` denominators rather than counted as misses, so an eval that ran 4 times, passed 3 and errored once reports `1.0`, and one whose every run errored reports `null` rather than a `0.0` that would claim it all failed; `evals:compare` reports error rates as their own section, treats a case that errored on every run of a side as NOT COMPARABLE rather than as a total regression, and declines to gate at all past `--max-error-rate` (default `0.05`), since the runs that survived may not be a fair sample of the ones that did not. The point of all of it is CI: with errors counted as failures, a rate-limited afternoon read as a model regression and failed the build.

- **Behavior Change**: `evals:compare --fail-on-regression` now requires a regression to be distinguishable from run-to-run variation, not just larger than the threshold. It was dividing one point estimate by another and comparing the ratio, while `baseline_stddev` and `candidate_stddev` sat unread on the same row - so at the repeat and case counts these runs actually use, it fired on noise, and a gate that fires on noise gets switched off. It also left unused the pairing both runs already had: the same dataset cases ran on both sides, and a consistent per-case move is separable from spread in a way that two independent means of the same numbers are not. Each regression row now carries a `p_value` alongside its `magnitude`, from an exact [sign test](https://en.wikipedia.org/wiki/Sign_test) over the matched cases (ties excluded) - or, for an eval with no dataset, an exact Fisher test on the repeat counts, since repeats are not pairs. The per-row level is the family-wise 0.05 divided by the number of rows that cleared the size threshold ([Bonferroni](https://en.wikipedia.org/wiki/Bonferroni_correction)): the gate fails if any row regresses, so testing 20 rows at 0.05 each would have failed one run in three on noise alone - a flakier gate than the one being fixed. Four consequences: `--significance ALPHA` is new, and `--significance 1` waives the evidence requirement to gate on effect size alone, which is what a dataset too small for a verdict needs (5 matched pairs cannot reach any conventional level however large the regression - 5 cases all moving the same way is p=0.0625); a run whose regressions are all untestable, which is what a gated score on a non-dataset eval produces, now exits **2** and says so rather than exiting 0 on a run that may well have regressed; pass-rate rows in `regressions` are now one per eval rather than one per case, since the cases are what the evidence is drawn from, and their `label` no longer carries a case id (per-case detail is unchanged under NEW FAILURES); and the text and HTML reports gain a REGRESSION GATE section showing each candidate row's size next to its evidence, so a withheld verdict is legible instead of mysterious. `Comparison#regressed?` and `#insufficient_evidence?` take an `alpha:` keyword; pass `alpha: 1` for the previous behavior.

- **Behavior Change**: a score summary's `stddev` and `ci95` are now taken over the same sample, and a new `spread_n` says what that sample was. `ci95` already resampled per-case means, deliberately, "so the interval reflects variation between inputs rather than between repeats of one input" - but the `stddev` printed immediately beside it, carrying the same `n`, was computed over every observation pooled. Pooling mixes real differences between inputs with repeat-to-repeat noise on one input, and for a dataset of any breadth the first dominates, so the figure described how varied the dataset was where a reader beside a mean needs to know how uncertain the mean is. A 20-case eval at `--repeat 3` now reports `n: 60, spread_n: 20`, with `stddev` and `ci95` both over the 20 per-case means; an eval with no dataset is unaffected, since there are no cases and both are over the individual values. `Comparison`'s `score_moves` rows get the same treatment (and the same new `spread_n`), restricted to the cases both runs share for the reason their means already were - a candidate sampled down to a subset must not have its spread measured over a different set of inputs than the baseline printed next to it.

- **Behavior Change**: `Raif::Evals::Statistics.stddev` is now the sample standard deviation, dividing by n-1 rather than n. Its own comment justified the population formula as "these are all the runs there were, not a sample of a larger set", which contradicts the rest of the feature: `--repeat` exists because each run is a draw from the model's output distribution, the docs call the repeats "independent samples", and the figure is printed to stop a reader over-reading a difference in means - an inference about the distribution behind them. Dividing by n understated the spread by 0.71x at n=2 and 0.89x at n=5, which is the range these runs live in, and understating it defeats the only reason it is shown. This narrows the bias rather than removing it: the square root of an unbiased variance is still biased low (about 0.80x at n=2), which is what `bootstrap_ci95` is for. Any recorded `stddev` in an existing results file was computed the old way; `evals:compare` does not read the key, so comparisons across the change are unaffected.

- **Breaking change**: evals now carry a stable `eval_id`, and it - not the eval block's position - is what identifies an eval across runs. `evals:compare` was matching a baseline result to its candidate on `eval_index`, the block's ordinal position in its eval set, so inserting or deleting an eval block shifted every index below it and the comparison quietly joined one eval's baseline to a different eval's candidate, printing the candidate's description over another eval's numbers. `--resume` had the same key and the same problem: editing the file between the interrupted run and the resume could skip the wrong executions while re-paying for ones already recorded. Every result now carries an `eval_id` of the form `MyEvalSet#slug-of-the-description-<12 hex>`, where the digest is `SHA256("<eval set class name>\n<description>")` - derived, so nothing has to be declared, and taken over the description verbatim, so `"handles > 100 items"` and `"handles < 100 items"` stay distinct even though they slug identically. The comparison key is now `[eval_id, case_id]` and the resume key `[eval_id, case_id, run_index]`. `eval_index` is still on every result and still means the block's position, which is what sorts results back into definition order within one run. Three consequences for host apps: two evals in one eval set can no longer share a description (their derived ids would be identical, so their results would be joined as though they came from one eval) and this raises when the class loads; `eval "...", id: "my-key"` overrides the derived half of the id, for when a description is reworded but should keep its history; and an eval set that is never assigned to a constant now raises when its evals run, since `#<Class:0x...>` changes every process and ids derived from it would make every comparison read NOT COMPARABLE. Results files written before this change have no `eval_id`: `evals:compare` refuses them rather than joining every result on `nil`, and `--resume` refuses such a log rather than skipping the whole run.
- **Breaking change**: an eval run's `configuration` block records a new `judge_model_key`: the model that actually judged, rather than only the `evals_default_llm_judge_model_key` that was configured. `evals:compare` refuses to diff two runs judged by different models, but it was reading the configured setting, which is `null` for every run that never configured a judge - so two runs of two different models, neither configuring a judge and each therefore graded by its own model under test, both recorded `null` and compared as though one ruler had been used for both. That is the exact case the check exists for. `Raif::Evals::Comparison` now reads `judge_model_key` and no longer falls back to the configured setting, so results files written before this change compare as though no judge was recorded; re-run the evals to produce comparable files. `judge_model_key` is also part of the `--resume` compatibility check, and the refusal message now explains that an unconfigured judge means the model under test.
- An eval run now warns, before it spends anything, when LLM judge expectations will be graded by the model under test. With no `Raif.config.evals_default_llm_judge_model_key` configured, judging falls back to `default_llm_model_key`, so the zero-configuration path is a model grading its own output - and the documented way to compare two models, `RAIF_DEFAULT_LLM_MODEL_KEY=... bundle exec raif evals`, moves the judge along with the subject. `evals:compare` already refuses to diff two runs judged by different models, but it cannot see this case, because both runs record the same unset judge key; the run that creates the problem is the only place it can be reported. The run header now names the model that will judge rather than printing a blank judge key (`(not set - judged by open_ai_gpt_4o, the model under test)`), the summary annotates it the same way, and a new `Raif::Evals::LlmJudge.resolved_llm_model_key` is the one place that resolves which model judges. The docs gained guidance on picking a judge: hold it fixed across everything you intend to compare, and prefer a model from outside the family under test.
- **Breaking change**: deciding what a `Raif::Evals::EvalSet` should run has moved off the eval set and onto a new `Raif::Evals::EvalSetCoordinator`. An `EvalSet` instance is a DSL execution context - `eval`, `setup`, `teardown`, and `dataset` blocks are `instance_exec`'d against one, and `expect`/`score` write onto the `current_eval_result` it carries - which makes it single-use and single-threaded by construction. It was also being used as the long-lived thing that resolved datasets, listed pending executions, and dispatched them to the worker pool, so half the instances in a run carried a meaningless `@current_eval_result` and the other half a meaningless run log, and the distinction survived only in a local variable named `coordinator`. Those responsibilities (`run`, `pending_executions`, `executions_for`, `result_order`, `run_and_record`) are now the coordinator's, one per eval set per run. `EvalSet.run(...)` is unchanged and still the way a host app runs a set on its own; it builds a coordinator internally. `EvalSet#run`, `#pending_executions`, `#executions_for`, `#result_order`, and `#run_and_record` are gone as instance methods, as is `#run_eval_definition`, which had no callers. `EvalSet#initialize` now takes only `output:`, since `run_log:`, `writer:`, and `header:` belong to the coordinator. `cases:`, `sample:`, and `seed:` are constructor arguments on the coordinator rather than parameters of `run`, `pending_executions`, `executions_for`, and `result_order`: they scope the coordinator, whose datasets are resolved once and read by every one of those methods, so a second set of values could only have been silently ignored. `Raif::Evals::Run` also builds one coordinator per eval set rather than one per command-line entry, so the same file named twice no longer resolves its datasets twice. A new `EvalSet#resolve_dataset(name)` evaluates one dataset block, which stays on the eval set because a dataset block is user DSL and can call `file`/`files`/`json`/`jsonl`. Custom expectation helpers, eval set subclasses, and everything in the results JSON are unaffected.
- **Breaking change**: `Raif::Evals::EvalSet.evals` now holds `Raif::Evals::EvalDefinition` objects rather than plain hashes. Every other link in the chain already had a class - `EvalCase` for one dataset input, `Dataset` for a collection of them, `EvalResult` for what running an eval produces - and the eval declaration itself was the one thing still a hash, which left `eval_index` with nowhere to live. It was a property of the definition's position, so it was threaded as a separate keyword through `executions_for` and `run_eval`, and re-derived by an O(n) `evals.index(definition)` identity scan in three places. An `EvalDefinition` carries its own `index`, assigned when it registers, and those parameters and lookups are gone. The attributes are `description`, `block`, `dataset`, `index`, `file`, and `line_number` - the last two renamed from `definition_file` and `definition_line_number`, which were only qualified that way to disambiguate keys in a hash that also held the eval's own description. `dataset?` replaces truth-testing the `dataset` key. Nothing in the results JSON changes, and `eval_index` there means exactly what it did; only code introspecting `EvalSet.evals` directly needs updating, from `definition[:description]` to `definition.description`.
- Eval runs can now overlap their provider calls. `raif evals --concurrency N` (with a `RAIF_EVAL_CONCURRENCY` environment equivalent and a `Raif.config.evals_concurrency` default) runs N eval executions at once across a bounded thread pool. The default is 1 and the serial path is byte-for-byte unchanged: same order, same output, no threads, no executor wrapping. An eval run is almost entirely spent waiting on responses - a 30-case dataset at `--repeat 5` with a judge call per case is 300 sequential round trips - so this is the wall clock. The whole run's work is listed before any of it executes, across every eval set rather than one set at a time, which keeps the threads busy over eval set boundaries, parallelises non-dataset evals, and resolves every dataset up front so a missing fixture fails before the first eval has been paid for. Concurrency needs a database connection pool larger than itself, since each eval holds a connection for the transaction it runs in; that is validated at startup and refused with a message naming `config/database.yml`, because the alternative is a run that spends itself timing out on checkouts and dies looking like a database problem rather than a setting. On sqlite3 it is capped to 1 instead, since concurrent write transactions against one file serialize on `SQLITE_BUSY`. Console lines arrive in completion order rather than definition order (every line already carries its case id, and each eval's description is printed when its first result lands), and each execution's lines - a case summary and the failing expectations beneath it - are emitted as one block rather than interleaved with whatever else finished at the same moment. Ctrl-C stops workers before they take their next execution and lets the in-flight ones finish and reach the run log, so everything already paid for stays resumable. Concurrency is deliberately not part of the results `configuration` block: it changes neither what a result means nor which cases produce one, and recording it would make `--resume` refuse to pick a run back up at a different concurrency, which is exactly what someone whose run just died to rate limits wants to do.
- Results in the results JSON are now written in definition order - eval block, then dataset order, then repeat - rather than the order they completed in, so two runs of the same work produce the same file whatever concurrency produced them. Dataset order is the order the dataset declares its cases in, not alphabetical by `case_id`. `summary.eval_pass_rates` and `summary.score_summaries` `per_case` rows are ordered the same way for the same reason. `evals:compare` joins on keys rather than position, so nothing about comparison depended on the previous order.
- `Faraday::TooManyRequestsError` (HTTP 429) is now in the default `Raif.config.llm_request_retriable_exceptions`. It is a `ClientError` rather than a `ServerError`, so it was not covered by the existing entry and rate-limited requests failed on the first try. `Raif::Utils::TransientRetry` now also honors a `Retry-After` response header when the provider sends one (seconds only - the HTTP-date form no LLM provider sends would need a trusted clock), and applies 25% jitter, since concurrent callers rate limited at the same instant would otherwise retry at the same instant and keep colliding. Both delay paths are jittered, and a `Retry-After` is the one that most needs it: a 429 is what produces N callers limited at once, and the header is the most likely reason they would then agree on a delay to the millisecond. The exponential delay is jittered down, so it stays under `max_delay`; a `Retry-After` is jittered up, since returning before the provider said to only buys another 429. `Retry-After` is honored past `max_delay`, which bounds Raif's guess rather than the provider's own instruction, and is capped instead by the new `Raif::Utils::TransientRetry::MAX_RETRY_AFTER_DELAY` (300 seconds) so a provider asking for an hour cannot hang a run. Pass `jitter: 0` for an exactly reproducible backoff curve.
- **Behavior Change**: `Raif::Llm#retry_with_backoff` now passes the provider's `retriable_exceptions` to `Raif::Utils::TransientRetry` instead of letting it fall back to `Raif.config.llm_request_retriable_exceptions`. The per-provider override existed but was never reaching the retry, which meant `Raif::Llms::Bedrock` - whose errors are AWS SDK classes that none of the config defaults match - retried nothing at all, including throttling. That list has also been narrowed from `Aws::BedrockRuntime::Errors::ServiceError` to the transient errors specifically (`ThrottlingException`, `ServiceUnavailableException`, `InternalServerException`, `ModelTimeoutException`, `ModelNotReadyException`): `ServiceError` is the base class for every Bedrock error, so retrying it would also retry `ValidationException` and `AccessDeniedException`, which no amount of waiting fixes and which retrying only delays.
- Setup and teardown failures no longer take a run down with them. An exception in `setup` was already recorded against the case that raised it, but `teardown` ran outside that rescue: a raise there propagated out of the execution before its result reached the run log, aborting the whole run and - under `--concurrency` - every other execution in flight, while discarding inference the failing case had already been billed for. Each stage of an execution now runs in its own rescue and records a `"Setup execution"`, `"Eval block execution"`, or `"Teardown execution"` error expectation against that one result. A failed `setup` still skips the eval block, since there is nothing coherent for it to run against.
- LLM calls made by `setup` and `teardown` are now reported instead of silently dropped. They stay out of a result's `usage` and out of the run summary's `total_*` figures - a fixture built by an LLM is not what the eval measures, and `evals:compare` reads `total_cost` across runs recorded by earlier versions, so its meaning has to hold still - but they are real spend, and a run summary that omitted them understated the bill for any suite whose fixtures are generated. A result whose surrounding blocks made calls gains an `overhead_usage` object of the same shape as `usage` (omitted entirely when they made none), the `summary` gains `total_overhead_model_completions`, `total_overhead_tokens`, and `total_overhead_cost`, and the console prints a line for it under `LLM Usage`. The model completion sink is now open across the whole execution rather than only the eval block, with the split decided by offsets taken around the block; a `teardown` that destroys the records is still safe, since the sink holds the objects rather than re-querying them.
- `expect_llm_judge_score` now checks for a colliding score name before it calls the judge rather than after. Recording the same score name twice in one eval raises, which is intended, but the raise landed on the way back from the judge - so the collision cost a judge request and then propagated out of the eval block, discarding every expectation that had already passed in it. The check now sits next to the `score_name:` check for string rubrics, which already ran first for the same reason.
- Eval sets can now run one eval body over many inputs. A new `dataset :name do ... end` class macro registers an ordered collection of cases, and `eval "...", dataset: :name` runs the body once per case, times the number of `--repeat`s, each in its own transaction with its own `setup`. `setup` and the eval block receive the case as an optional block argument, so existing zero-arity blocks are called exactly as before and adding a dataset to one eval never requires touching its siblings. A case is a plain hash of `id` (required, and the join key `evals:compare` matches on), `input` (required), and `expected` (optional); inside the blocks it arrives as a `Raif::Evals::EvalCase` exposing `id`, `input`, `expected`, and `[]` reading through to `input`. `jsonl(name)` and `json(name)` read from a new `raif_evals/datasets` directory (created by `raif evals:setup`), and a new `files(glob)` globs `raif_evals/files` and returns paths relative to it so they compose with the existing `file` helper; a dataset block can also just return an array built any other way, since Raif imposes no row schema beyond those three keys. A missing or duplicated case id raises when the dataset resolves, which happens before the run executes any eval, because a case that cannot be told apart from another produces results that cannot be diffed and finding that out after paying for the inference is too late. A `dataset:` naming an undeclared dataset raises when the class body loads, so datasets must be declared above the evals that use them. An exception in one case is recorded against that case only and the rest of the dataset still runs; that now covers `setup` as well as the eval block, since a bad fixture is the likeliest way for a single case to blow up and it previously aborted the whole run. Setup failures are recorded against a "Setup execution" expectation rather than "Eval block execution". Each result in the results JSON carries a `case_id`, and `summary.eval_pass_rates` rows for a dataset eval gain `eval_index`, `cases`, `repeats`, and a `per_case` breakdown; rows for a non-dataset eval keep exactly the keys they had. Console output goes compact for dataset evals (one line per case per repeat with the pass count and scores, failing expectations printed beneath), with the full per-expectation output still available under `--verbose`. A failing expectation's description is truncated to 100 characters on those lines and in the text comparison report, since an LLM judge expectation is described by its entire criteria and the same one repeats under every case that failed it, which at full length buries the case ids and counts the line exists to show; `label:` on the judge helpers chooses what appears there, and the untruncated text stays in the results JSON, the HTML report, and `--verbose` output.
- Added `--cases a,b,c`, `--sample N`, `--seed N`, and `--[no-]verbose` to `raif evals`, with `RAIF_EVAL_CASES`, `RAIF_EVAL_SAMPLE`, `RAIF_EVAL_SEED`, and `RAIF_EVAL_VERBOSE` environment equivalents alongside the existing `RAIF_EVAL_REPEATS`. `--verbose` still only turns verbose output on, but `--no-verbose` can now turn it off, because an app that sets `evals_verbose_output = true` in its initializer could otherwise never reach the compact dataset output the flag exists to protect - verbose prints every expectation for every case, and that is precisely the output a multi-case dataset makes unreadable. Passing neither leaves the configured value alone. A full dataset run costs real money, so these ship with datasets rather than after them. Sampling under a `--seed` draws the same cases again, which is what makes a sampled run comparable against another; without one it draws differently each time. `--cases` filters every dataset in the run, so an id belonging to one eval set's dataset simply skips the others, but an id that matches nothing anywhere exits non-zero rather than reporting a suite of zero evals that passed. A sampled run always ends up with a seed: when `--seed` is not given Raif draws one, prints it in the run header, and records it, so a run sampled without thinking about seeds is still reproducible case-for-case afterwards. It also has to be recorded for `--resume` to work - the seedless draw is fresh entropy on every invocation, and since both invocations would record `seed: null` the resume compatibility check compares them equal, so a resumed run would sample a different subset and complete the results file with two unrelated samples in it. A resume adopts the seed the log header holds rather than drawing again. The effective `sample` and `seed` are recorded in the results `configuration` block.
- Judge scores are now first-class results rather than metadata. A new `score "name", value, scale:, min:, max:, higher_is_better:` records a number on the eval result, gating the eval when `min:` and/or `max:` is given and purely observing it when neither is, and `expect_llm_judge_score` emits one automatically, named after its rubric and carrying the rubric's scale (via a new `Raif::Evals::ScoringRubric#scale`) and its `min_passing_score`. Each eval result gains a `scores` array and the run's `summary` gains `score_summaries`, one row per score name per eval with `n`, `mean`, `median`, `stddev`, `min`, `max`, a 95% bootstrap `ci95` over cases, and `per_case` means. `expectation_results` and `result_metadata` are untouched, so existing consumers that re-derive scores from metadata keep working. A suite made only of pass/fail expectations has a ceiling: once two models clear every bar their results are identical, and the quality regression that arrives before a bar is missed is invisible. The gate and the direction are independent: `higher_is_better:` says which way is good and feeds `evals:compare`'s improvement-versus-regression call, while `min:`/`max:` say where the eval starts failing, so a lower-is-better metric gets a ceiling and a metric that can be wrong in either direction gets both. The gating expectation is named after the comparison it performs (`clarity score >= 4`, `elapsed_ms score <= 5000`, `bullet_count score >= 3 and <= 7`). Recording the same score name twice for one eval raises: the summary aggregates by name, so two of them would be averaged into one row where a regression in one can be masked by an improvement in the other, and values drawn from a single response would be counted as independent samples, narrowing the confidence interval on correlated data. `expect_llm_judge_score` therefore takes a `score_name:` overriding the rubric-derived name, for the case where one eval judges two things against the same rubric and wants them tracked apart, and requires it when the rubric is passed as a string: a `ScoringRubric` names the score itself, a string has no name to derive one from, and a placeholder would put a metric nothing can be told about into the summary and make two string rubrics in one eval collide after the first judge call had already been paid for. The check runs before the judge does. The pass/fail expectation's description is unchanged (a string rubric still reads `LLM judge score (custom): >= 7`), since that description is how `evals:compare` matches a result to its counterpart in a run recorded by an earlier version. `stddev` and `ci95` are omitted when there is only one observation to compute them from, and `evals:compare` likewise omits the standard deviation from a score move whose two sides both have one: the arithmetic returns `0.0` and a zero-width interval for a single value, which in a summary read to decide whether a difference is real would claim a spread had been measured when none was.
- Added `raif evals:compare BASELINE.json CANDIDATE.json`, which diffs two eval runs. Results are matched on eval set, `eval_index`, expectation description, and `case_id`; matching per case rather than per eval is what makes a dataset run diffable, since a model can improve on average while getting materially worse on one input. It prints new failures, fixes, score moves with a per-case breakdown, and cases or expectations present in only one run, which are reported rather than dropped because a silently omitted case looks exactly like agreement. `--fail-on-regression N` exits non-zero when a pass rate or a gated score gets more than `N` worse than the baseline *as a fraction of it*, so the command can gate a script; ungated observational scores are reported but never trip it, and a score declared `higher_is_better: false` counts a decrease as an improvement. The threshold is relative rather than absolute because a pass rate, a 1-5 rubric score, and a latency in milliseconds are not in the same units, and one absolute threshold cannot mean the same thing to all three - `0.25` would ask for a quarter of an eval's runs on one row and a quarter of a millisecond on the next, which fires on noise until the flag gets turned off. Relative to what each quantity started from, `0.25` asks one question everywhere: did anything get more than 25% worse. A pass rate that started at 1.0 gives the same number either way, so the common case is unaffected. A regression from a baseline of zero (a gated `error_count` going from 0 to 3) has no fraction to take, and is reported with a null magnitude that trips any threshold rather than being skipped for want of a denominator. Two runs judged by different models are refused with exit code 2 rather than warned about, since scores from two judges measure two different things and a warning printed above a ranking is too easy to scroll past; `--allow-judge-mismatch` overrides it. `--format` takes `text` (default), `json`, or `html`, the last writing a self-contained report next to the candidate results file. The diff itself lives in `Raif::Evals::Comparison`, which is pure Ruby over the two parsed payloads, and the command deliberately does not boot Rails: the one part of the eval tooling that needs no database and no API key should not be the slowest to start.
- Added `Raif.config.evals_capture_model_completions`, which takes `:full` (the default, and unchanged behavior), `:summary`, or `:none`. Full capture includes every prompt, message, and response, which is what you want when debugging a single eval and unmanageable for a dataset run, where it can produce a results file of tens of megabytes. `:summary` keeps the per-call token counts and cost but drops the text; `:none` omits the `model_completions` array entirely. The per-eval `usage` object and the run's `summary` totals are identical in all three modes, and the effective mode is recorded in the results `configuration` block so a later reader can tell a deliberately trimmed capture from a run that made no LLM calls.
- The built-in LLM judge helpers now accept `judge_attributes:`, and eval sets can define `judge_task_attributes` to supply attributes to every judge they run. `Raif::Evals::LlmJudge` inherits from `Raif::Task`, so an app that has extended `Raif::Task` with a required column (a non-nullable tenant or account id, for example) previously could not use the built-in judges at all: the judge task's insert failed and took the surrounding eval's transaction with it. `judge_task_attributes` is called per eval after `setup`, so it can reference what `setup` created, and an individual expectation can add to or override it. All three helpers also accept `label:`, which replaces the criteria-derived expectation description for cases where the criteria is a paragraph. Note that a label is part of how `evals:compare` matches a result to its counterpart in an earlier run, so editing one reads as the old expectation disappearing and a new one arriving.
- Fixed `expect_llm_judge_score` never printing the judge's score. Its first positional parameter was named `output`, which shadowed the eval set's `output` method, so the `output.puts "Score: ..."` call was made against the content string and guarded by a `respond_to?(:puts)` check that was always false. The parameter is now named `content`; the call is positional, so no caller changes.
- Fixed `raif evals path/to/eval_set.rb` failing when the file had already been loaded in the same process. The eval set class was found by diffing `Raif::Evals::EvalSet.subclasses` across the `require`, and `require` is a no-op for an already-loaded file, so the diff came back empty and the run crashed on `nil.name`. Eval definitions now record the file they were defined in, and the class is found that way when the diff is empty.
- **Breaking change**: renamed `Raif::Evals::Eval` to `Raif::Evals::EvalResult`, and `Raif::Evals::EvalSet#current_eval` to `#current_eval_result`. The class was never an eval - the eval block and its description live in `EvalSet.evals`, and this object is the outcome of running one of them once. The old name made "eval" mean both the definition and the result, which becomes actively misleading now that a single eval block can be run against many inputs. No keys in the results JSON change; host apps only need to update custom expectation helpers that reach for `current_eval` rather than going through `expect`.
- `Raif::Evals::EvalSet.eval` now raises `ArgumentError` when called without a block. The eval set DSL's `eval` shadows `Kernel#eval` inside the class body, so a block-less call - which is what reaching for `Kernel#eval` there looks like - previously registered an eval whose block was `nil`. That failed only once the eval ran, after `setup` had already spent inference money, and surfaced as `instance_eval`'s "wrong number of arguments (given 0, expected 1..3)" recorded against an "Eval block execution" expectation. It now fails when the class body loads, before any provider request.
- Added xAI Grok 4.6 (`x_ai_grok_4_6`, API name `grok-4.6`): 500K context, text and image input, native tool calling and structured outputs. xAI does not offer this model on its Batch API, so it is registered with `supports_batch_inference: false` like `x_ai_grok_4_5` and batch callers fall back to the synchronous path. Note that xAI bills requests whose prompt reaches 200K tokens at double the listed per-token rates.
- Added Grok 4.6 via OpenRouter (`open_router_grok_4_6`, API name `x-ai/grok-4.6`) with image input, native tool calling, and structured outputs. OpenRouter routes to the standard xAI endpoint at $2.00 / $6.00 per million tokens by default; its priority endpoint costs double, and prompts at or above 200K tokens bill at double rates on every endpoint.
- Added an opt-in archive-and-cull capability for old `Raif::ModelCompletion` rows (new migration; run `rails raif:install:migrations` when upgrading). **Disabled by default**: with `Raif.config.archive_enabled` false (the default) and no storage adapter configured, upgrading changes nothing and Raif never deletes anything. When enabled, hosts schedule `Raif::ArchiveModelCompletionsJob` (e.g. nightly); each run selects completions older than `Raif.config.model_completion_retention_period` that pass every safety guard (24h quiescence; for terminal rows a fresh `Raif::InferenceCostEvent`, meaning present and at least as recent as the completion; citations copied to the conversation entry; no membership in a non-terminal batch), serializes them as gzip JSONL with a versioned manifest (full attribute round-trip; batches are bounded by both record count and uncompressed byte size), uploads via the `Raif.config.archive_storage` adapter (required contract: `write(key:, io:, checksum_sha256:)` returning a nonblank location string and raising on any failure - a blank return aborts the run before anything is recorded or deleted; `Raif::ArchiveStorage::FileSystem` ships as a reference implementation and verifies the written file against the checksum), records a `Raif::Archive` audit row, and then, in a single locked transaction, re-checks eligibility, stamps `raif_archive_id` on the completions' cost events, and deletes the rows. Nonterminal completions older than the cutoff (orphaned pending rows from crashed or killed processes, which would otherwise be immortal) are archived and culled through the same path; they have no cost event, so v1 keeps no per-record link from their source back to the archive that holds them (recovery is a search over candidate objects via `Raif::Archive.covering`). The guarantee is at-least-once archiving plus never-delete-unarchived: a crash anywhere simply causes the next run to re-archive under a new storage key (a harmless duplicate object), so there is no state to repair. The `raif_archive_id` stamp on the cost event is the authoritative link from culled spend to its archive; `Raif::Archive.covering(resource_type:, record_id:)` is an operator forensic helper that lists the candidate archive objects whose id range covers a record (newest first), which a range match alone cannot prove membership of. Operators can preview a run anytime with `Raif::ArchiveModelCompletionsJob.dry_run`, which writes nothing and reports eligible counts plus per-guard exclusions. `Raif.config.validate!` rejects retention periods under 1 month so a misconfigured value can never reach inside an open billing window. The web admin gains an Archives section (index/show; payloads are not browsable, the row is the audit trail), a retention banner on the model completions index, an "Archived" badge with durable cost/token data on task and conversation entry pages whose completion was culled, and archive settings on the config page. Archives contain full prompts and responses; the storage target must be private, encrypted, and access-controlled at least as strictly as your application data.
- Added per-tenant partitioning and complete partition erasure to the archival capability above. `Raif.config.archive_partition_column` (default nil, preserving unpartitioned keys, manifests, and behavior exactly) names a column on the archived resource, e.g. a host-added `account_id`; when set, every archive object holds records from exactly one partition and is stored under `raif-archives/partitions/<sha256 of the normalized value>/<resource-type>/...`. The partition prefix sits above the resource type, so deleting one prefix erases every archived resource type for that partition, including crash-orphaned uploads that have no `Raif::Archive` row; storage paths carry only the SHA-256 token, never the raw host identifier (the normalized value is stored on the new indexed `raif_archives.partition_value` column and recorded in the manifest as `partition_column`/`partition_value`). The partition column's value must be immutable for a record's lifetime; the locked cull re-checks it and aborts the batch (removing the tainted object and its audit row, best-effort) if it changed mid-upload. Records whose partition value is NULL or normalizes to blank fail closed - retained, never archived, reported by `dry_run` as `excluded_by_missing_partition` - unless the host explicitly sets `Raif.config.archive_partition_fallback = Raif::ArchivePartition::UNGROUPED` (aliased as `Raif::Archive::UNGROUPED`; the canonical constant is eagerly required so host initializers can reference it) to archive them under a reserved `_ungrouped` segment that partition purges can never match. `Raif::ArchiveModelCompletionsJob#perform` now takes three work budgets (`max_records: 100_000`, `max_objects: 500`, `max_runtime: 30.minutes`) in place of `max_batches:` and schedules work in round-robin passes, at most one object per partition per pass with partitions visited oldest-eligible-first, so many small partitions drain within a run while one large-backlog partition cannot monopolize it; `dry_run` additionally reports per-partition eligible counts. `Raif::Archive.purge_partition!(partition_value:)` performs the erasure: it requires only a storage adapter implementing `delete_prefix` (deliberately independent of `archive_enabled` and the partition column, since erasure obligations outlive feature flags), takes the same advisory lock as the archive job (raising the retryable `Raif::Errors::ArchiveBusyError` when busy so the two can never interleave), deletes the partition's storage prefix first, then transactionally nullifies surviving cost event stamps and deletes the partition's `Raif::Archive` rows; it is retry-safe in both directions (a storage failure leaves DB audit state intact; a DB failure after prefix deletion re-runs cleanly) and returns a structured summary (normalized value, prefix, objects removed, rows deleted, stamps nullified, duration), also emitted via `ActiveSupport::Notifications` as `purge_partition.raif`. Raif persists no purge audit record of its own; hosts persist what they need from the returned summary. The storage adapter contract gains optional idempotent `delete(key:)` and `delete_prefix(prefix:)` methods (required only when the corresponding feature is used; `Raif::ArchiveStorage::FileSystem` implements both with storage-root containment validation). The admin archives pages display each archive's partition value; purging is programmatic only, with no admin UI.
- **Behavior Change**: `Raif::InferenceCostEvent.backfill!` (and `Raif::RepairInferenceCostEventsJob`, which runs it) now also re-syncs stale events - events older than their completion, e.g. a post-terminal completion update whose event sync failed - instead of only creating missing ones. An accurate-but-stale event gets its freshness certified via a timestamp touch after a successful re-sync. This pairs with the archive job's freshness guard: a terminal completion whose event is missing or stale is never culled, so hosts enabling archiving should schedule `Raif::RepairInferenceCostEventsJob` periodically (e.g. daily) to keep such rows self-healing.
- Fixed `x_ai_grok_4_5` producing no output whatsoever via the Batch API while working normally on the synchronous endpoint. xAI rejects the model at batch-file validation ("JSONL file validation failed: Model grok-4.5 is not supported for batch processing"), so `x_ai_grok_4_5` is now marked `supports_batch_inference: false` and callers that guard on it fall back to the sync path automatically. `grok-4.3` and both `grok-4.20` variants batch normally and are unaffected. Batch support is no longer assumed uniform across a provider: `Raif::Llm#supports_batch_inference?` now honors a `supports_batch_inference` entry in `model_provider_settings`, defaulting to the provider's class-level capability, so a single model can be opted out without disabling batching for the whole adapter. Note the class-level `Raif::Llms::XAi.supports_batch_inference?` remains `true` – check the instance (`Raif.llm(key).supports_batch_inference?`) to get the per-model answer.
- **Behavior Change**: the xAI batch adapter no longer reports a rejected or unparsed batch as successfully completed. xAI has no batch-level state enum and leaves every count in `state` at zero both *before* it has parsed the uploaded JSONL and *after* it has rejected the batch, so the previous `num_pending == 0` terminal rule fired on a batch that had not started (or would never start), immediately marking it `ended`, fetching an empty result stream, and force-failing every child completion with "xAI batch entry missing". Terminal now additionally requires `num_requests > 0`, and a `cancel_by_xai_message` in the response maps the batch to `failed` with `failed_at`, `failure_error` ("xAI rejected batch"), and xAI's verbatim message in `failure_reason` – previously the reason was discarded entirely and the batch landed terminal with a null `failure_reason`. Also fixed the expiry field name: xAI returns `expire_time` (a date), not `expires_at`, so `Raif::ModelCompletionBatches::XAi#expires_at` and the `expired` status branch had always read `nil` and could never fire. `provider_response` now stores `expire_time` and `cancel_by_xai_message` (readable via the new `#rejection_message`) rather than `expires_at`; host apps reading `provider_response["expires_at"]` on an xAI batch should switch to `#expires_at` or `provider_response["expire_time"]`.
- **Behavior Change**: `raif_evals/setup.rb` is now loaded before the eval set files rather than after. Loading an eval set evaluates its class body, so anything setup.rb defines for the sets to use (shared helper modules, scoring rubrics) previously did not exist yet and an `include` of it raised `NameError`. Setup code that depended on eval set classes already being loaded will need to move.
- Eval runs are now attributable to the model that produced them, and can be repeated to produce a pass rate. The results JSON gains a top-level `configuration` block recording `default_llm_model_key`, `evals_default_llm_judge_model_key`, and `repeats`, and the model key is appended to the results filename (`eval_run_<timestamp>_<model_key>.json`) so several models' results can sit side by side in `raif_evals/results`. A new `--repeat N` CLI flag (or `RAIF_EVAL_REPEATS=N`) runs each eval N times, re-running `setup` and the eval block each time so the repeats are independent samples of a non-deterministic model; each result carries a `run_index` and an `eval_index` identifying which eval block produced it, and the run's `summary` gains `eval_pass_rates` (one row per distinct eval with `runs`, `passed`, and `pass_rate`), which is also printed to the console. Pass rates are grouped by `eval_index` rather than description, since the DSL does not enforce unique descriptions and two same-named eval blocks would otherwise collapse into a single blended row. The model and judge keys are printed in the run summary header. Host apps that glob `raif_evals/results/eval_run_*.json` are unaffected, but anything matching the exact previous filename format will need updating.
- Fixed native structured-output requests failing with a 400 (`Faraday::BadRequestError` on Anthropic, `ValidationException` on Bedrock) when a task's `json_response_schema` declares a value constraint. Anthropic's structured-output validator accepts a narrower slice of JSON Schema than tool `input_schema` does, and rejects the whole request rather than ignoring the constraint (e.g. "For 'integer' type, properties maximum, minimum are not supported"). Schemas declaring `minimum`/`maximum` on an `integer` or `number`, `maxItems`/`uniqueItems` on an `array`, or `minProperties`/`maxProperties` on an `object` therefore worked on the `json_response` tool-call path but failed as soon as a request qualified for `output_config` -- most visibly when provider-managed WebSearch was disabled, since that is what selects the native path. Both adapters now transform the schema before sending it (see the `Raif::Llms::Anthropic::StrictSchemaTransformer` entry above); Bedrock is covered too, since its Converse endpoint forwards the Anthropic validator's message verbatim rather than validating the schema itself.
- **Behavior Change**: Anthropic JSON responses via the synthetic `json_response` tool (the path used when provider-managed WebSearch suppresses native structured outputs) are now schema-enforced and repair-tolerant. On models that support structured outputs, the tool is sent with `strict: true` so the API constrains the tool input to the schema. A dedicated `Raif::Llms::Anthropic::StrictSchemaTransformer` removes constraint keywords that Anthropic strict schemas reject (`minimum`/`maximum`, `exclusiveMinimum`/`exclusiveMaximum`, `multipleOf`, length/size and property-count bounds, `uniqueItems`, `pattern`, and `patternProperties`) from both synthetic tool schemas and native `output_config.format` schemas, folding each removed constraint into the property's `description` so the model still sees it. Literal data under `enum`, `const`, `default`, and `examples` is preserved unchanged. Schemas using `contains` raise `Raif::Errors::UnsupportedFeatureError` before the provider request because Anthropic does not support the keyword and Raif's local validator cannot enforce it. `minItems` gets special handling because Anthropic's strict subset supports values of 0 and 1: larger bounds are clamped to `minItems: 1` on the wire instead of dropped, so constrained decoding still rejects empty arrays, with the real bound preserved in the description and in the caller's original schema. The transformation is schema-aware: user-defined names under `properties`, `$defs`, or `definitions` are preserved even when they collide with a constraint keyword (e.g. a property named `minimum`). Response extraction also normalizes degenerate tool inputs that models occasionally emit: a payload nested under a `json_response` key is unwrapped, a double-encoded JSON string payload is decoded, and unknown root properties are removed when the schema forbids them. Repaired candidates must still satisfy the caller's original schema; unusable candidates fall back to text blocks. A directly returned empty object remains valid when the caller's schema allows it, while a malformed stub is not repaired into an empty object. The same extraction repair and validation now apply to AWS Bedrock's synthetic `json_response` tool (the path used by models without native structured outputs support, e.g. `bedrock_claude_5_sonnet`); Bedrock's Converse API has no strict tool input option, so repair is the only available defense there. The shared repair logic lives in `Raif::Llms::SyntheticJsonResponseToolInputNormalizer`, called explicitly by both adapters. Host apps that pin request cassettes to the previous non-strict Anthropic tool definition or native output schema will see differences.
- Anthropic native structured responses are validated locally against the caller's original schema after the provider response completes. This restores enforcement of constraints removed from the provider-facing schema; violations raise `Raif::Errors::InvalidJsonResponseError` while preserving the response for diagnosis. The error is not retried by Raif automatically, so host applications retain control over retry policy and inference spend.
- Removed the vestigial `json_response` tool-call extraction branch from the OpenRouter adapter. Since OpenRouter JSON responses moved to `response_format: json_schema` with `provider.require_parameters`, requests no longer include the synthetic `json_response` function tool, so no response could contain a matching tool call; `extract_json_response` now reads the message content directly.
- Added `Raif::InferenceCostEvent`, a slim durable per-completion cost/token record (new migration; run `rails raif:install:migrations` when upgrading). An event is created automatically when a `Raif::ModelCompletion` reaches a terminal state (completed or failed) and survives deletion of the completion row: the `raif_model_completion_id` foreign key is nullified at the DB level (`ON DELETE SET NULL`, so raw `delete_all` culls are safe) while `original_model_completion_id` is retained forever for correlation. Events copy the completion's token counts, costs, model keys, source (including the concrete STI class in `source_class_name`), and `incurred_at` (mirroring the completion's `created_at`, the time axis for windowed cost queries). Host apps can attach their own context via the new `Raif.config.inference_cost_event_metadata` resolver, and disable creation entirely with `Raif.config.inference_cost_events_enabled = false` (default `true`). A sync failure never fails the completion save: the error is reported via `Rails.error` and the idempotent `Raif::RepairInferenceCostEventsJob` is enqueued to self-heal (hosts may also schedule it periodically as a safety net). Destroying a terminal completion whose event has not been persisted yet syncs the event first; if that sync fails, the destroy is aborted (a deleted completion cannot be repaired, so the spend record would otherwise be lost permanently).
- **Behavior Change**: `Raif::ConversationEntry#citations` and `#llm_model_key` are now local columns (new migration; run `rails raif:install:migrations` when upgrading), copied from the winning model completion when the entry is finalized, so historical conversations keep their citation chips and model key after old completion rows are culled. Idempotent.
- **Behavior Change**: Raif's admin stats (`Raif::Admin::StatsController`, `Raif::Admin::Stats::TasksController`) and agent inference stats (`Raif::Agent#total_cost` and friends) now read from `Raif::InferenceCostEvent` instead of re-summing `raif_model_completions`, so they keep working after old completion rows are culled. **After upgrading, run the backfill promptly** (`rails raif:backfill_inference_cost_events`, `BATCH_SIZE` env var optional): these stats read events immediately and will show partial history until the backfill completes.
