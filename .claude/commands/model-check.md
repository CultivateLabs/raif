# Model Check

Patrol raif's model registry for drift against provider reality. Arguments (optional): a provider name, a concern ("pricing openai"), a URL, or a free-text tip. With no arguments, ask first: "Anything specific that prompted this, or general sweep?"

Rules that apply to every step:
- Research first, report second, act only after explicit approval. Never edit files before the user picks items to act on.
- One PR-sized branch per concern, suggested and created only with the user's agreement. NEVER run `git commit`, `git push`, or open a PR yourself: propose each commit (staged file list plus drafted message) and act only after the user approves it.
- No em dashes or en dashes in anything you write (CHANGELOG, commits, docs). No AI attribution in commits. Keep wording generic to raif.
- Provider documentation plus the user's approved proposal determines manifest truth. Smoke output is supporting runtime evidence. Never change a declared capability solely because a generic API request failed.

Steps:
1. Read `lib/raif/model_manifest/definitions/*.rb`. Note each provider's `references` URLs, including `api_versions` where present.
2. Gather, scoped by the user's hint when given: fetch the reference URLs (WebFetch), search the web for announcements since the newest `added_on`, and where a provider has a public list-models API and a key is configured, list it (OpenAI GET /v1/models, Anthropic GET /v1/models, xAI GET /v1/models, OpenRouter GET /api/v1/models, Google GET /v1beta/models).
3. Report findings in these groups, each item with its source cited. The groups through the smoke observations are a cross-reference against the manifest. The last four (API versions, parameter deprecations, beta headers, endpoint deprecations) are read from the pins, request paths, and capability claims in `app/` and `lib/`, and their sources are read on every run, not only for announcements since the newest `added_on`:
   - models available upstream but absent from the manifest
   - carrier availability gaps: a model family in the manifest under a direct provider that Bedrock or OpenRouter now lists (per that carrier's models_doc reference or public list-models API) with no corresponding manifest entry, and the reverse: a Bedrock or OpenRouter entry whose direct provider is integrated in the manifest but lacks the model. A carrier listing shows the model is offered, not that a given account or region can invoke it; verification happens locally via /model-add and bin/smoke
   - pricing differences (manifest per-million vs published)
   - pricing annotations needing re-verification: entries whose `pricing[:valid_until]` is past (promote any `followed_by` rate to the listed rate, then drop `valid_until`, `followed_by`, and the promotional `note`) or within 30 days without a `followed_by` rate, and entries whose `pricing[:note]` describes a promotion the provider no longer documents
   - announced deprecations or retirements not recorded in lifecycle fields
   - recorded retirement_dates within 60 days or past
   - deprecated models whose replacement_key is itself deprecated, or with neither replacement_key nor migration_note
   - models with unverified or stale capabilities (per `bin/smoke --stale 30`'s selection logic: read `model_smoke_results/*.json` for missing or old successful observations against positively claimed, recordable capabilities; do not run bin/smoke or hit live APIs for this)
- API versions: find the pins by searching `app/` and `lib/` for constants named `API_VERSION` or `API_BASE_URL`, and read that provider's `api_versions` reference. Report `<provider> api version: <pinned value>` when it documents a dated version newer than a dated pin, or a deprecation or end date for the pinned value. A coexisting path version, such as Google `v1` beside `v1beta`, is not a finding unless the pinned value itself is deprecated or given an end date. Give the pinned value, the latest version, the listed changes that touch request fields Raif's request builders for that provider send, the keys those changes affect, whether the pinned version is affected yet (a migration guide may let requests stay on the old version), and the source. When none of the changes touches a field Raif sends, still report it and say "No affected manifest keys identified".
- parameter deprecations: a request parameter that the provider's `api_versions` or `deprecations` reference documents as deprecated, removed, or rejected by some models or versions, where the request builder sends it only when a capability is true (for example `temperature`) and an entry claims that capability. Report `<provider> parameter deprecation: <parameter>` with those keys and whether the pinned version is affected yet. Skip parameters no capability gates.
- beta headers: for each `*_beta_header` default in `lib/raif/configuration.rb`, read the current docs for the feature it enables. Report `<provider> beta header: <value>` when the feature is documented as generally available, even if the header is still accepted, or when the header is retired or replaced; say which. List the entries claiming the capability the header serves (for `anthropic_message_batches_beta_header`, `batch_inference`). Report nothing while the feature is still beta and that exact value is still the one to send.
- endpoint deprecations: find the endpoints Raif calls by searching the adapters under `app/models/raif/llms/`, `app/models/raif/embedding_models/`, and `app/models/raif/concerns/llms/` for request paths passed to the HTTP connection (including paths returned by methods such as `api_path`) and Bedrock SDK client operations such as `converse` and `invoke_model`. Report `<provider> endpoint deprecation: <endpoint>` when the provider's `deprecations` or `api_versions` reference announces a deprecation or shutdown of one of them. Give the endpoint as the provider names it, the Raif path or operation it matches, the announcement and shutdown dates, the replacement, the keys served by that adapter (for batch and file endpoints, the entries claiming `batch_inference`; for embedding endpoints, the embedding model keys), and the source. Skip an endpoint named only as the replacement for something else, and deprecated endpoints Raif does not call.
- for these last four groups, affected keys are active and deprecated entries; leave retired entries out. If a source a group needs cannot be fetched or read, report `<provider> <category>: unverified` with the URL and the error. Never treat an unread source as no drift.
4. Ask which findings to act on (AskUserQuestion, multiSelect). Whenever any provider under check has models with missing or stale smoke observations, the question MUST include a "Smoke <provider> models (bin/smoke --record)" option alongside the other findings, even when no other finding needs action. This is the only place in the workflow where a live smoke run is offered, so it is never dropped to keep the list short.
5. For each approved finding, ask: handle here sequentially, or write a handoff doc per concern to `docs/handoffs/` (Goal / Current State / Key Decisions / Next Steps format) for parallel sessions.
6. Acting on a finding in-session:
   - smoke run (missing or stale observations): before running anything, state the scope in chat: the selectors (exact keys, a provider prefix such as `google` or `x_ai`, or `--stale 30`; OpenAI needs both `open_ai` and `open_ai_responses` since the first prefix excludes responses keys; see `bin/smoke --help`), how many models that covers, that it spends real API credits, that batch_inference probes poll for up to 10 minutes each, and that provider-managed image_generation is skipped unless run with `--only provider_managed_tools`. Missing credentials for that provider block the run; say so instead of running. On approval run `bin/smoke <selectors> --record`; `--record` writes only hard-oracle passes to `model_smoke_results/<provider>.json` and never edits the manifest. Present the full matrix. FAIL and NOTE are investigation prompts, not manifest edits: research each against provider documentation, propose a specific correction with citations, edit only after approval, then re-smoke that capability with `bin/smoke <key> --only <capability> --record`. Stage the updated `model_smoke_results/<provider>.json` together with whatever manifest change it accompanies in this session (pricing, deprecation, or addition) so the evidence lands with the change it verifies; only when nothing else changed, propose it as its own commit on the current branch
   - pricing update: edit the manifest pricing (when the published rate is promotional or time-limited, write the published rate and add `note:` and, if an end date is documented, `valid_until: Date.new(...)`, plus a `followed_by:` rate when the provider publishes the rate that follows), run `bundle exec rspec spec/lib/raif/model_manifest_validity_spec.rb`, add a CHANGELOG bullet, suggest a `model-pricing-<provider>` branch, and propose the commit (diff, files to stage, drafted message) for the user to approve
   - new model: switch to the /model-add workflow with what you learned
   - deprecation/retirement: switch to the /model-retire workflow
   - API version, parameter deprecation, beta header, or endpoint deprecation: handling it here means drafting a scoped follow-up in chat (what would change, the affected keys, the sources). Do not edit the pin, the capability claim, the header, the adapter, or any manifest entry, and do not switch to /model-retire. Bumping a version, changing a claim, or retiring keys because their endpoint shuts down is the user's decision, taken in that follow-up
   - if the user supplied a URL that proved useful, add it to that provider's `references` in the manifest
